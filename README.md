# TeethTech CRM MVP

Отдельный продукт для тестирования и обучения сотрудников. Backend — **Go 1.26**, frontend — Next.js / React. Go-приложение самостоятельно создаёт базу, применяет встроенные SQL-миграции и подготавливает учебные учётные записи. Исходные проекты не изменяются.

Сохранён существующий модуль заказов: клиники и карточки пациентов/врачей, виды работ, направления, зубы, цвета и материалы изделий, цены заказа, задачи, автоматические и предварительные назначения, канбан, разрешённые переходы, история, файлы, контроль качества и возвраты на доработку. Есть рабочая зона сотрудника, календарь и личные заметки. После завершения всех задач заказ закрывается; возврат закрытой задачи на доработку или добавление новой задачи снова открывает заказ.

Бухгалтерские и складские API, начисления зарплаты, резервы и списания отключены. Материалы как характеристики изделия и цены заказа сохранены. Схема данных и отдельные пакеты доменов сохранены для расширения. В этой поставке флаги MVP_WAREHOUSE_ENABLED и MVP_FINANCE_ENABLED должны оставаться false; дальнейшее подключение этих модулей потребует разработки и проверки Go API. Чат и внешние интеграции отложены; рабочие доски обновляются через HTTP каждые 10 секунд, телевизионная доска — каждые 30 секунд.

## Запуск на обычном компьютере

Нужен компьютер с Docker и Docker Compose v2, интернет для первой сборки и свободный порт 8090. Для Windows/macOS используйте Docker Desktop (на Windows включите WSL2); на Linux — Docker Engine с Compose. Практический ориентир: 8 ГБ оперативной памяти, 15 ГБ свободного диска. Linux/macOS-скриптам нужен Python 3. Windows-скрипты используют только PowerShell и Docker.

Скопируйте всю папку `teeth-tech-crm-mvp` на компьютер. Рабочие данные сохраняются в отдельных Docker volumes и переживают перезапуск.

Windows — откройте PowerShell в папке продукта:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start.ps1
```

Linux/macOS — откройте терминал в папке продукта:

```sh
./scripts/start.sh
```

Первый запуск собирает оба приложения, создаёт отдельные PostgreSQL и MinIO для вложений (собирается из исходников), применяет миграции, проверяет готовность и выполняет smoke-проверку входа, заказов, заметок и KPI. В зависимости от интернета сборка может занять несколько минут.

Откройте **http://localhost:8090**. Администратор: **admin@teethtech.kz**. Пароль — значение `MVP_ADMIN_PASSWORD` в созданном `.env`. Пароли генерируются отдельно для каждого запуска на новом компьютере; `.env` не входит в поставочный архив. При повторном старте они не меняются. Изменение `.env` после первого старта не сбрасывает пользовательские пароли; меняйте их через настройки пользователя.

Для первой установки можно вместо открытого пароля задать `MVP_ADMIN_PASSWORD_HASH='BCrypt-хеш'` и оставить `MVP_ADMIN_PASSWORD` пустым. Одинарные кавычки обязательны для символов `$`. При входе вводится исходный пароль, не хеш. Готовый хеш имеет приоритет. Проверка `smoke` в этом режиме проверяет доступность; для полной проверки входа передайте исходный пароль через `MVP_SMOKE_ADMIN_PASSWORD`.

Учебные сотрудники: `dispatcher@teethtech.kz`, `plasterer@teethtech.kz`, `scanner@teethtech.kz`, `ceramist@teethtech.kz` (точный список виден администратору в «Лаборатория → Сотрудники»). Их общий **учебный** пароль — `MVP_TRAINING_PASSWORD`. Для ежедневной работы создайте собственные учётные записи с отдельными паролями. Если оставить `MVP_TRAINING_PASSWORD` пустым до первого запуска, унаследованные учебные аккаунты получат неизвестные случайные пароли.

Другие сотрудники в локальной сети открывают **http://IP-КОМПЬЮТЕРА:8090**. Например, `http://192.168.1.20:8090`. Разрешите входящие подключения TCP 8090 в брандмауэре компьютера, убедитесь, что устройства находятся в одной сети. В `.env` можно задать `MVP_PUBLIC_URL=http://192.168.1.20:8090`, затем выполнить `docker compose up -d`. Компьютер должен оставаться включённым. База и файловое хранилище наружу не публикуются.

Для внешнего доступа через интернет поставьте HTTPS-прокси перед этим компьютером. HTTPS-прокси должен передавать правильные Host/Origin и схему; локальная конфигурация предназначена для HTTP в сети. Автоматический выпуск сертификатов в эту поставку не включён.

## Работа и обучение

Откройте **«Обучение»** — инструкции и упражнение на 15 минут. Сначала настройте роли и направления сотрудников, затем создайте учебный заказ. При автоматическом назначении задача передаётся сотруднику с ролью следующего этапа; сначала выбираются профильные сотрудники, затем учитывается нагрузка. Каждый сотрудник работает под своей учётной записью и подтверждает завершение этапа комментарием. Главный техник проверяет результат и возвращает задачу при необходимости.

Личные заметки доступны только владельцу, сохраняются 30 дней с последнего обновления. Постоянные сведения о заказе сохраняйте в его комментариях.

## KPI

- Администратор и главный техник: **«KPI сотрудников»**, `/kpi`.
- Сотрудник: **«Мой KPI»**, `/employee/kpi`; сервер всегда ограничивает отчёт текущим пользователем.
- Период включает обе выбранные даты в `Asia/Aqtobe` (UTC+5), максимум 367 дней.
- «Этапы» — подтверждённые переходы по workflow, включая повторное завершение после доработки.
- «Закрытые задачи» — уникальные задачи, перешедшие в конечный статус за период, отдельно для каждого исполнителя. Повторное закрытие тем же исполнителем не увеличивает число задач и единиц.
- Запись фиксирует исполнителя **до** передачи задачи следующему сотруднику и отдельно того, кто подтвердил переход. Название работы, номер заказа и количество сохраняются снимком.
- Статистика начинается с запуска MVP; прошлые события старого продукта автоматически не импортируются. Возврат на доработку не удаляет прежнее завершение из исторического отчёта.
- Итоги считаются по всему периоду; список событий загружается страницами. Нажатие на сотрудника фильтрует отчёт.

## Обслуживание

```sh
docker compose ps
docker compose logs --tail 100 backend frontend
# Остановить, сохранив данные:
docker compose stop
# Повторно запустить:
docker compose up -d --wait
```

Полная копия базы, вложений и настроек: Linux/macOS — `./scripts/backup.sh`, Windows:

```powershell
powershell -File scripts/backup.ps1
```

Нужен Python 3.9 или новее. Скрипт кратковременно останавливает приложение, сохраняет согласованную копию в `artifacts/backups/full-*` и запускает сервисы снова. Успешная копия имеет файл `COMPLETE` и контрольные суммы в `manifest.json`. Храните копию на другом носителе: она содержит приватные настройки. Команда `docker compose down -v` удаляет данные: не используйте её для обычной остановки.

## Проверки разработчиком

```sh
cd backend
go test -race ./...
cd ../frontend
npm ci
npm run typecheck
NODE_OPTIONS=--no-experimental-webstorage npm test
npm run build
cd ..
./scripts/smoke.sh
```

После запуска продукта выполните `python3 scripts/test-backend.py`: автономные интеграционные тесты Go создают отдельную временную БД `teethtech_mvp_go_test` и удаляют её после проверки. Нужны Docker и Python 3; Java, Maven и Redis не нужны. Проверяются миграции с нуля, повторный запуск, авторизация, заказы, вложения и multipart-загрузка, KPI, доработка, одновременное закрытие, права доступа, заметки и доставка внутренних уведомлений. Результаты — в `VALIDATION.md`.

При обновлении ранее созданного Java-MVP Go сверяет контрольные суммы всех старых миграций и принимает его существующую базу. Заказы, учётные записи, KPI и файлы сохраняются. Предыдущая Java-сборка для работы больше не требуется.

Для переноса продукта на другой компьютер: `./scripts/package.sh`. Архивы `artifacts/teeth-tech-crm-mvp.zip` и `artifacts/teeth-tech-crm-mvp.tar.gz` содержат исходники и инструкции без `.env`, зависимостей, сборок и рабочих данных. Распакуйте его в отдельную папку и выполните запуск для своей ОС.

Хранилище MinIO собирается из зафиксированного исходного релиза [RELEASE.2025-10-15T17-29-55Z](https://github.com/minio/minio/releases/tag/RELEASE.2025-10-15T17-29-55Z), поэтому запуск не зависит от доступности старого `minio/minio` в Docker Registry. Это увеличивает время первой сборки.


Статусы настраиваются в «Лаборатория → Статусы»: рабочие этапы можно создавать, отключать и активировать. Нельзя отключить этап с текущими задачами; сначала завершите или переведите их. Системные «Новая задача», «Ожидание проверки», «Завершено» защищены от удаления, отключения и изменения флагов.

Новая установка Go MVP запускается без учебных заказов, промежуточных этапов и маршрутов. Старые справочные виды работ отключены; создайте свой вид работы с цепочкой этапов в «Лаборатория → Виды работ». Роль в каждом этапе — сотрудник, выполняющий этот этап; приём и закрытие выполняет диспетчер. Перезапуск сохраняет ваши настройки. Обновление ранее установленного MVP автоматически данные не удаляет.

Для явной очистки только конфигурации в базе без заказов: `python3 scripts/reset-workflow.py` (Windows: `python scripts/reset-workflow.py`). Скрипт делает резервную копию, сохраняет сотрудников и системные статусы и отказывается работать при наличии заказов или задач. Отключение статуса в маршруте блокирует новые заказы по нему до повторной активации.

### Параллельный пилот в лаборатории

Первые 5 рабочих дней ведите 10–20 заказов в CRM и привычном журнале. В комментарии заказа указывайте номер из журнала. Назначьте ответственного за ежедневную сверку: пациент, врач, конструкция, зубы, материал/цвет, сроки, назначенный техник, этапы, качество, выдача и получение клиникой. Используйте отдельные учётные записи сотрудников. Для ошибок записывайте номер заказа, пользователя, время, действие, ожидаемый и фактический результат.

Новые заказы требуют входного контроля в карточке: задание врача, качество/комплектность данных, компоненты; для физических материалов — подтверждение обработки по протоколу лаборатории. Имплантные работы дополнены системой и платформой/соединением. Согласование дизайна можно сделать обязательным перед конкретным этапом или завершением производства. Подтверждение фиксирует сотрудник с именем врача и основанием в комментарии; это запись полученного согласования, а не отдельный вход врача.

«Лаборатория → Приём и выдача» показывает также заказы с завершённым производством. Проверка качества и передача клинике записываются отдельно, с пользователем и временем. Открытые инциденты блокируют выдачу. Изменение конструкции/задач и доработка сбрасывают проверку качества. Уже выданное изделие требует оформленного возврата с категорией причины. Материалы, партии и серийные номера сохраняются для прослеживаемости изделия без складского учёта.

При ожидании указывается причина; производственные переходы блокируются. Уведомления SLA этапа приостановлены; при возобновлении его контрольные сроки продлеваются на реальное время ожидания. Срок заказа для клиники автоматически не переносится: новый срок должен согласовать диспетчер. Дата приёма пациента и срок производства — отдельные поля.

Полная резервная копия: `./scripts/backup.sh` или Windows `powershell -File scripts/backup.ps1`. Сохраняются база, все данные MinIO, `.env` и контрольные суммы. На время копирования приложение кратковременно останавливается и затем запускается; выполняйте после смены. Готовая копия имеет файл `COMPLETE`, находится в `artifacts/backups/full-*` и содержит приватные настройки. Копируйте её на другой носитель с ограниченным доступом. Эти данные не включаются в поставочный ZIP.

Критерии завершения пилота: нет потерь заказов/файлов и критических расхождений с журналом; назначение, ожидание, согласование, доработка, контроль качества и выдача проверены сотрудниками; руководитель разобрал ошибки; проверены резервная копия и запуск после перезагрузки. Автотесты проверяют технические сценарии, а соответствие реальной работе подтверждается этим пилотом.

## SaaS-пилот для 2–3 лабораторий

Добавлена отдельная Go-панель владельца с регистрацией по приглашению. Владелец создаёт лабораторию и копирует ссылку для руководителя; email указан в приглашении, пароль руководитель задаёт сам. Ссылки не отправляются автоматически. Приглашение действует 7 дней и принимается один раз. В панели можно продлить пилот, приостановить или возобновить доступ, перевыпустить или отменить неиспользованное приглашение. Пилот начинается после готовности CRM. По истечении срока доступ блокируется, worker останавливает установку; данные сохраняются.

Для каждой лаборатории создаются отдельный Docker Compose project `teethtech-pilot-lab1` / `lab2` / `lab3`, PostgreSQL, MinIO, volumes, сеть, JWT и пароль хранилища. В новой лаборатории виден один зарегистрированный руководитель; учебные сотрудники и клиники скрыты, заказы и маршруты пусты. Руководитель добавляет своих сотрудников, клиники и этапы. Панель владельца показывает состояния, сроки и события управления; заказы и KPI остаются в CRM лаборатории. Единого входа владельца во все заказы пока нет.

Этот режим проверен на macOS/Docker Desktop и рассчитан на Linux-сервер с Docker Compose v2 и Python 3.9+. Windows для SaaS worker не поддерживается (блокировка процесса использует `fcntl`). Обычная отдельная CRM сохраняет прежние скрипты запуска.

Локальный запуск из корня продукта:

```sh
python3 scripts/saasctl.py setup
python3 scripts/saasctl.py build
python3 scripts/saasctl.py start
python3 scripts/saasctl.py status
```

Панель: `http://localhost:8099`. Email владельца: `SAAS_OWNER_EMAIL`, пароль: `SAAS_OWNER_PASSWORD` в отдельном приватном `saas/.env`. Пароль и BCrypt существующего MVP не меняются. Лаборатории доступны через `http://lab1.localhost:8099`, `lab2.localhost:8099`, `lab3.localhost:8099`. Эти адреса предназначены для локальной демонстрации. Первая сборка требует интернета для зависимостей и образов.

На сервере задайте реальные адреса до первого приглашения:

```sh
python3 scripts/saasctl.py setup --public-url https://crm.example.kz --base-domain example.kz --owner-email owner@example.kz
python3 scripts/saasctl.py build
python3 scripts/saasctl.py start
python3 scripts/saasctl.py edge-config
```

Если `saas/.env` существует, `setup` сохраняет его. До первой инициализации отредактируйте `SAAS_PUBLIC_URL`, `SAAS_BASE_DOMAIN` и email в нём. После инициализации смена email/пароля в файле не изменяет существующую учётную запись владельца. Для смены публичного адреса остановите панель и worker командой `stop`, измените настройки и выполните `start`. Старые ссылки при смене домена перевыпустите.

Настройте DNS для `crm.example.kz`, `lab1.example.kz`, `lab2.example.kz`, `lab3.example.kz` на сервер. Установите Caddy на хост, используйте сгенерированный `saas/.saas-runtime/Caddyfile` и откройте для него порты 80/443. Внутренние адреса: панель `127.0.0.1:8099`, база управления `127.0.0.1:55432`, лаборатории `127.0.0.1:12001..12003`. Их не открывайте наружу. HTTPS на публичном адресе нужен для безопасных cookie. Реальный сервер, DNS и выпуск TLS-сертификатов в этой сессии не проверялись.

Запуск после перезагрузки Linux:

```sh
python3 scripts/saasctl.py systemd-config
python3 scripts/saasctl.py stop
sudo cp saas/.saas-runtime/teethtech-portal.service /etc/systemd/system/
sudo cp saas/.saas-runtime/teethtech-worker.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now teethtech-portal teethtech-worker
```

Генерируйте units от пользователя, который собрал продукт и имеет доступ к Docker. Пути и пользователь подставляются автоматически; проверьте их на целевом Linux-сервере. При systemd управляйте процессами через `systemctl`, а не одновременно через `saasctl start`. PostgreSQL панели и контейнеры лабораторий имеют `restart: unless-stopped`. Worker запускается на хосте; веб-панель не получает Docker socket. Приватные журналы доступны в runtime или через `journalctl` при systemd.

Отдельные резервные копии:

```sh
python3 scripts/saasctl.py backup lab1
python3 scripts/saasctl.py backup lab2
python3 scripts/saasctl.py backup-control
```

Копия лаборатории содержит SQL, MinIO, `.env`, её `compose.yaml`, `nginx.conf` и SHA-256 manifest; база управления копируется отдельно с настройками панели. Храните оба вида копий на другом носителе. Runtime расположен в `saas/.saas-runtime` и исключён из поставочных архивов. Не удаляйте volumes и не меняйте project name при переносе данных. Остановленная лаборатория после backup остаётся остановленной; работающая CRM кратковременно недоступна при копировании.

### Все лаборатории, расписание и внешние копии

```sh
python3 scripts/saasctl.py backup-all
python3 scripts/saasctl.py verify-backup /absolute/path/to/backup
python3 scripts/saasctl.py backup-timer-config
sudo cp saas/.saas-runtime/teethtech-backup.service /etc/systemd/system/
sudo cp saas/.saas-runtime/teethtech-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now teethtech-backup.timer
systemctl list-timers teethtech-backup.timer
```

Таймер запускается ежедневно в 03:00 по Asia/Aqtobe, с задержкой до пяти минут. `backup-all` копирует базу панели и каждую созданную лабораторию, включая приостановленные. Для приостановленной CRM временно запускается только PostgreSQL, затем снова останавливается. Отдельная блокировка защищает от одновременного бэкапа и действий worker. Копии лабораторий последовательные: это не единый атомарный снимок всех установок. Работающая CRM кратковременно недоступна при своей копии. Ошибка любой лаборатории отражается в общем ненулевом коде завершения; остальные лаборатории всё равно копируются.

Результат: `saas/.saas-runtime/backup-reports/latest.json`. Проверка целостности отвергает незавершённые копии, изменённые/пропущенные файлы, символические ссылки и небезопасные пути. Контрольные суммы не заменяют тест восстановления и не являются криптографической подписью: нарушитель с доступом к хранилищу может изменить и файлы, и manifest.

Полный комплект также сохраняет `images.tar` с образами контейнеров, чтобы восстановление не зависело от доступности старых версий в registry. Это увеличивает размер каждой общей копии. Новые лаборатории закрепляют образы отдельными тегами версии и запрещают их незаметную загрузку извне. Старые установки с bare image IDs нужно отдельно перевести на сохраняемые теги; если старого образа уже нет локально, комплект копии завершится с ошибкой `images`, даже когда SQL и файлы успешно скопированы. Не удаляйте старые версии образов, пока на них работают лаборатории и пока не проверен комплект восстановления.

Для старой лаборатории: `python3 scripts/saasctl.py repair-images lab1`. Если локального образа уже нет, команда сохраняет приватный образ из существующего контейнера; если нет и контейнера, останавливается с ошибкой. Восстановленные runtime-образы могут содержать переменные окружения с секретами: храните их только в приватных копиях, не публикуйте в registry. `python3 scripts/saasctl.py update-frontend lab1` сохраняет предыдущую версию, делает копию и обновляет только frontend на проверенный образ из `SAAS_FRONTEND_IMAGE`; при ошибке запуска возвращает предыдущую конфигурацию. Остановленная лаборатория остаётся остановленной. Обновления backend и схемы базы требуют отдельного плана миграции и отката.

Без внешнего хранилища команда явно предупреждает, что копии только локальные. Для зашифрованной отправки установите `age` и `rsync`, создайте каталог на отдельном сервере в РК и настройте SSH-ключ с проверкой host key. В приватный `saas/.env` добавьте оба значения:

```dotenv
SAAS_BACKUP_AGE_RECIPIENT='age1...публичный_ключ_получателя...'
SAAS_BACKUP_REMOTE='backupuser@backup.example.kz:/srv/teethtech-backups'
```

Публичный ключ age используется для шифрования полного комплекта до отправки. Закрытый ключ храните отдельно от CRM-сервера; без него восстановить зашифрованные копии нельзя. Удалённый каталог должен существовать. Ошибка шифрования/отправки приводит к ошибке `backup-all`, а не к отметке об успешной внешней копии. Контроль доступа и шифрование диска основного сервера нужны отдельно: локальные полные копии содержат `.env`, пароли хранилища и персональные данные.

Срок хранения предлагается согласовать с лабораторией: например, 7 ежедневных и 4 недельных внешних копии. Автоматическое удаление старых копий не включено, чтобы не потерять единственную исправную версию. До запуска на реальных данных настройте ротацию у поставщика хранилища, контроль свободного места и уведомления о сбое копирования. Результат `systemctl status teethtech-backup.service` сам по себе не отправляет уведомлений владельцу. Внешняя отправка и Linux-таймер требуют проверки на выбранном сервере.

### Окончание доступа и возврат данных

Сейчас SaaS управляет сроком пилота, а не платёжной подпиской: webhook оплаты и автоматическое продление после оплаты не реализованы. Отказ клиента продолжать означает ручную приостановку владельцем; истёкший срок блокируется автоматически. Доступ через домен лаборатории закрывается сразу, worker затем останавливает контейнеры. База и файлы сохраняются; домены и слоты не передаются новому клиенту. Продление срока само по себе не запускает остановленную CRM: после него требуется «Возобновить».

Данные не удаляются автоматически и сейчас сохраняются до отдельного согласованного действия администратора. Это нужно явно сообщить в условиях пилота. Рекомендуемый процесс: сообщить руководителю об окончании доступа, предложить выгрузку, согласовать срок хранения (например, 30 дней), а перед окончательным удалением подтвердить запрос у уполномоченного руководителя. Не обещайте автоматическое удаление через 30 дней: такой механизм не реализован. Ротация резервных копий определяет, когда удалённые данные исчезнут и из копий; срок и исключения нужно согласовать отдельно. Общая копия панели содержит сведения обо всех лабораториях и не выдаётся клиенту.

```sh
python3 scripts/saasctl.py export-data lab1
```

Выгрузка работает и для приостановленной лаборатории, сохраняет её остановленной и содержит SQL с данными лаборатории и файлы MinIO. `.env`, ключи хранилища и Compose-конфигурация в клиентский архив не включены. В SQL остаются технические записи пользователей, включая хеши паролей; это техническая полная выгрузка, а не удобный Excel-отчёт. Архив находится в приватном `saas/.saas-runtime/exports` и содержит персональные данные. Проверьте полномочия получателя; передавайте архив через защищённый канал с ограниченным сроком доступа или отдельно зашифруйте ключом получателя. Общедоступной ссылки на скачивание нет. Перед возобновлением доступа после инцидента отзовите скомпрометированные сеансы и смените пароль, а не просто продлевайте срок.

### Восстановление и сопровождение

На отдельном изолированном сервере сначала выполните `verify-backup` для каждого компонента, включая каталог образов. Загрузите версии контейнеров командой `docker image load -i /absolute/path/images.tar`. Сохраните поставочный архив исходников той же версии для сборки панели и host-скриптов. Для CRM нужны `database.sql`, каталог `storage`, приватные `config.env`, `compose.yaml` и `nginx.conf`; для панели — `control.sql` и её настройки. В PostgreSQL должны существовать роли владельцев: `mvp` для CRM, `saas` для панели. Восстановите PostgreSQL до запуска backend, восстановите каталог MinIO в его volume при остановленном MinIO. Исправьте абсолютный bind-path `nginx.conf` при переносе на другой сервер. Затем запустите контейнеры, проверьте вход, заказ и скачивание вложения. Тестовую восстановленную установку не публикуйте под рабочим доменом и не подключайте к рабочим volumes. Перед заменой действующей базы сделайте отдельную текущую копию. Самостоятельной команды, перезаписывающей рабочую базу, намеренно нет.

После копирования MinIO восстановите владельца файлов `storage:storage` внутри volume при остановленном сервисе, иначе приватные права файлов могут препятствовать запуску. Образы из копии требуют совместимой CPU-архитектуры: ARM64-копия с локального Mac не заменяет сборку AMD64-версии на обычном VPS.

Проверочный инструмент создаёт уникальный Docker project с новыми volumes, восстанавливает SQL и MinIO, проверяет готовность и удаляет только созданные тестовые ресурсы. Gateway привязан к случайному порту `127.0.0.1`. Загрузка Docker-образов добавляет/восстанавливает их теги локально; выполнять на выделенной среде для восстановления.

```sh
python3 scripts/restore-check.py --lab-backup /path/to/lab-backup --images-backup /path/to/image-backup --control-backup /path/to/control-backup --email chief@example.kz
```

Пароль для проверки входа вводится скрыто; для автоматического теста можно передать `MVP_RESTORE_TEST_PASSWORD` через приватную среду процесса. Без `--email` проверяются восстановление SQL, запуск хранилища и готовность CRM, но не авторизованный вход. Даже успешный запуск не заменяет выборочную проверку конкретных заказов и скачивания рабочих файлов.

Новые установки используют актуальные образы, существующие закрепляют конкретные image IDs. `build` не обновляет уже созданные лаборатории. После успешных тестов обновляйте существующие установки в согласованное окно с предварительной копией и планом отката. Следите за обновлениями ОС, Docker, PostgreSQL, MinIO и frontend. Не открывайте базы, MinIO и Docker socket в интернет. Защита от объёмных DDoS требует возможностей провайдера; локальные проверки приложения не подтверждают устойчивость к такому трафику. До подключения реальных данных необходимы мониторинг, управление секретами и проверка восстановления на целевом сервере.

Образы установки закреплены по image ID. Повторные задания сохраняют существующие ключи и volumes; пересборка общих образов не обновляет уже созданные лаборатории автоматически. При переносе на другой сервер нужны пересборка образов и адаптация compose-файлов к новым путям/image ID; полное восстановление SaaS на другом хосте ещё требует отдельного прогона.

Основа изоляции: [Docker Compose project name](https://docs.docker.com/compose/how-tos/project-name/). Внешний вход: [Caddy reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) и [Automatic HTTPS](https://caddyserver.com/docs/automatic-https). Нагрузочная ёмкость целевого сервера пока не измерена.


Обновление лабораторного MVP: показатели сотрудников исправлены; справочник материалов доступен в «Лаборатория → Материалы» независимо от склада. Цвет в задаче можно оставить пустым, если он не нужен для работы. Очередь «Приём и выдача» поддерживает поиск по номеру, пациенту и клинике, фильтрацию этапа и страницы по 50 нарядов.

После сборки `python3 scripts/saasctl.py build` обновить Go и фронт выбранной установки можно командой `python3 scripts/saasctl.py update-application lab1`. Перед обновлением создаётся резервная копия, предыдущие образы сохраняются; при неудачном запуске возвращаются прежние образы. Для версий с изменением схемы БД нужен отдельный план миграции и восстановления: откат контейнера сам по себе не откатывает базу.

В разделе «Лаборатория → Технические справочники» администратор заполняет импланты и протетику, модельные системы, гарнитуры зубов и расцветки. Подсказки в лабораторном задании позволяют выбрать запись или указать индивидуальные параметры. Реквизиты сохраняются текстом в наряде: изменение каталога не меняет старые заказы. Изменение реквизитов самого задания сбрасывает входной контроль, согласование дизайна и контроль качества.

На производственной доске показано календарное время на текущем этапе с последнего перехода. Комментарии не сбрасывают таймер. Счётчики показывают неназначенные задачи и задачи на этапе три дня и дольше. Порог внимания включает время ожидания; это не норматив производства и не учёт рабочего времени техника.

В карточке заказа «Печатный наряд» открывает защищённую страницу с заданием, зубами, материалами, техниками и техническими реквизитами. Кнопка «Печать / PDF» открывает системный диалог печати. Суммы, QR-код, вложенные фотографии и журнал комментариев в этот бланк не включены. Новые технические каталоги изначально пусты.

Поддержка и сообщество работают через публичный адрес лаборатории, например `http://lab1.localhost:8099`, в общей SaaS-платформе. Прямой внутренний адрес контейнера и отдельная установка на 8090 не подключены к общей платформе. Учётная запись проверяется через Go API своей лаборатории при каждом обращении: данные из редактируемой клиентской cookie не используются как подтверждение личности.

В разделе «Поддержка» сотрудник создаёт заявку, читает ответы и прикладывает скриншоты вручную (PNG/JPEG, до 1 МБ, до трёх файлов на заявку). Автор видит свои заявки; администратор и главный техник видят заявки своей лаборатории. Владелец отвечает и меняет статус в общей панели: новая, в работе, ждём ответа, решена. Ответ сотрудника на решённую заявку открывает её снова. Переписка обновляется каждые 20 секунд. Вложения доступны только через проверку доступа к заявке; данные нарядов, пароли и токены автоматически не отправляются. Перед отправкой скриншота сотрудник должен скрыть сведения пациента. Отдельные email/Telegram-уведомления и автоматический ИИ-ответ пока не реализованы.

«Сообщество» — закрытая лента участников пилота, а не открытая социальная сеть для всех лабораторий. Руководитель добровольно разрешает показ публичного названия и города. Участники размещают вопросы, вакансии, предложения сотрудничества и новости, комментируют и отправляют жалобы. Публикации подписаны публичным названием лаборатории; email и идентификаторы сотрудников не показываются. Владелец видит причины жалоб и может скрывать публикации. Выход лаборатории скрывает её публикации и комментарии из общей ленты; записи сохраняются для модерации. Рабочие наряды остаются в отдельных базах.

Заявки, скриншоты и публикации хранятся в базе SaaS и входят в `backup-control` / `backup-all`. Резервная копия только отдельной лаборатории их не содержит. Команда `export-data` выгружает рабочие данные CRM, заявки поддержки со скриншотами и собственные записи сообщества этой лаборатории; записи других лабораторий не включаются. Автоматического удаления общих данных при прекращении подписки нет. Порядок хранения и удаления нужно закрепить в условиях сервиса до коммерческого запуска. После истечения пилота доступ через CRM блокируется, для поддержки руководитель связывается с владельцем вне CRM.

### Пациенты без ручных кодов и защита данных

В заказе сначала выбирается клиника, затем имя пациента. Повторный заказ с единственным совпадением использует прежнюю карточку. Для другого человека с таким же именем отметьте **«Новый пациент — отдельная карточка»**. При нескольких совпадениях выберите карточку: поиск работает по всей клинике, показывает последний заказ и позволяет открыть историю. Система сохраняет UUID пациента автоматически; клиникам и сотрудникам не нужно согласовывать или запоминать коды. Совпадение имени не доказывает, что это один человек: диспетчер должен проверить историю. Старые карточки и заказы сохраняются. Новая миграция разрешает однофамильцев, не объединяя существующие записи.

В панели владельца можно подключить двухфакторный вход: подтвердить пароль, добавить показанный ключ в приложение-аутентификатор и подтвердить шестизначным кодом. После подключения вход требует пароль и свежий код; повторное использование кода запрещено. Настройка относится к владельцу SaaS, не к аккаунтам сотрудников CRM. Секрет MFA хранится зашифрованным; для восстановления необходимо сохранить приватный `SAAS_WORKER_SECRET` вместе с конфигурацией, отдельно от публичных архивов. MFA не включается автоматически без подтверждения владельцем.

Ответы доменного API и скачивания файлов запрещают кэширование. Скачивания, выдача защищённой ссылки и просмотр истории пациента фиксируются в существующем журнале аудита. Общий поиск пациентов и врачей доступен администратору и диспетчеру; доступ к задачам и файлам продолжает проверяться по исполнителям/направлениям и лаборатории.

Новые установки SaaS создают приватный ключ резервных копий в `.saas-runtime/keys/backup.key`. Настройка `SAAS_BACKUP_KEY_FILE` включает дополнительный зашифрованный архив `.ttbk` для базы платформы, каждой лаборатории и образов Docker. Рабочие каталоги резервных копий остаются закрытыми локальными копиями для существующих инструментов восстановления; это не шифрование всей файловой системы сервера. На отдельное хранилище следует отправлять `.ttbk`, а ключ держать отдельно и иметь защищённую резервную копию ключа. Без ключа архив не восстановить. Внешняя отправка пока не настроена — нужен выбранный оператором адрес хранилища.

Команды для шифрования и восстановления (из корня проекта):

```sh
python3 scripts/encrypt-backup.py --generate-key --key /private/path/backup.key
python3 scripts/encrypt-backup.py /private/path/full-backup --key /private/path/backup.key --output /private/path/full-backup.ttbk
python3 scripts/decrypt-backup.py /private/path/full-backup.ttbk --key /private/path/backup.key --destination /private/path/new-restored-directory
```

Не генерируйте новый ключ вместо существующего: старые архивы требуют прежний ключ. Расшифрование проверяет целостность всего архива до извлечения и запрещает опасные пути/ссылки. После расшифрования используйте `verify-backup` и `restore-check.py`; восстановление проверяйте в отдельных временных томах.

`saasctl.py export-data lab1` теперь включает данные поддержки и сообщества **только указанной лаборатории** в каталоге `platform`, дополнительно к SQL и файлам CRM. Архив содержит чувствительные данные и хеши аккаунтов CRM: передавайте только проверенному представителю лаборатории по защищённому каналу. После отмены подписки доступ блокируется; данные автоматически не удаляются. Сроки хранения, подтверждение получателя, требования к согласию пациентов, доступу поддержки и удалению резервных копий нужно установить в договоре и операционных процедурах до работы с реальными пациентами. Эти изменения не заменяют юридическую проверку, внешнее хранилище, настройку сервера и независимый аудит безопасности.

Для первого пилота достаточно основного сервера и отдельного хранилища копий в другом аккаунте/у другого провайдера в Казахстане. Второй работающий сервер CRM не требуется. На сервере установите ежедневный таймер `backup-timer-config`, отправку зашифрованных копий во внешнее хранилище и проверку результата: наличие локального архива не подтверждает внешнюю отправку. Ключ храните также в защищённом менеджере секретов или на отдельном защищённом носителе. Регулярно выполняйте пробное восстановление; копирование кратковременно останавливает приложение, поэтому планируйте его вне смены. Период хранения копий и данных после окончания подписки согласуйте заранее.

### Настройка производственных маршрутов

Откройте «Лаборатория → Виды работ → Создать тип работы». Конструктор из основного проекта работает с Go API: укажите вид работы, добавьте промежуточные этапы и роли, расположите этапы перетаскиванием. Системные начало, проверка и закрытие добавляются сервером автоматически. В пустой форме доступны заготовки цифровой и керамической коронки. Они не создают данные до сохранения: проверьте названия, порядок и роли под вашу лабораторию. Существующие активные этапы используются повторно; если нужной роли нет, выберите или создайте её. Заготовки являются примерами, а не обязательным технологическим протоколом.

Справочник новой лаборатории начинается без старых демонстрационных типов работ. В «Создать тип работы» доступны девять заготовок: цифровая и керамическая коронка, циркониевая коронка/мост, пресс-керамика/винир, съёмный протез, работа на имплантах, временная коронка/мост, окклюзионная каппа и ремонт протеза. Заготовка сначала заполняет форму; запись появляется в справочнике только после сохранения. Материал, оборудование, примерки и ответственных адаптирует руководитель лаборатории. Маршруты показывают организационные этапы и не задают режимы оборудования или обязательные клинические протоколы. Ориентиры по направлениям работ: [Ivoclar workflows](https://www.ivoclar.com/en_gb/workflows/workflow-overview) и [Formlabs application guides](https://dental.formlabs.com/indications/guides/).

### Аналитика производства

`/analytics` — отдельная доска руководителя, `/kpi` — журнал результатов сотрудников. Доска показывает активные работы, просрочки, сроки на сегодня и ближайшие три дня, проверку, завершённые работы текущего месяца и среднюю длительность завершённых работ. Нагрузка этапов, исполнителей, клиник и материалов считается по всем работам в доступной пользователю области, до ограничения карточек. Это число работ, а не оценка трудоёмкости. Средний срок считается от создания работы до её последнего завершения, включая ожидание и возвраты; это не время труда техника.

Подборка внимания ограничена 12 приоритетными работами, фильтры переключают эту подборку; полные счётчики остаются над ней. Из карточки можно открыть заказ. Сроки и граница месяца используют `Asia/Aqtobe`. Автообновление раз в минуту при открытой вкладке, плюс ручное обновление. Материал может учитываться в нескольких работах, одна работа — в нескольких материалах. Финансовые показатели в производственный обзор не включены.

Демонстрация: <http://lab1.localhost:18192/analytics>. Проверка браузером: `PLAYWRIGHT_MODULE=/path/to/playwright-core node scripts/analytics-browser-check.cjs` (только отдельная демоустановка со стандартными демоаккаунтами).

### Подсказки в карточке заказа

Блок «Приёмка и передача заказа» показывает путь заказа и инструкцию «Что нужно сейчас» с ответственным, последовательностью действий и ожидаемым результатом. Подсказка меняется для приёмки, производства, ожидания, согласования врача, инцидентов, отказа проверки, выдачи, получения и возврата. Кнопка ведёт к нужному разделу или задачам заказа. Для роли без права проверки / выдачи объясняется, кому передать работу.

Комментарий запрашивается в окне конкретного действия. Там есть пример, обязательные поля и объяснение результата. Отмена и Escape закрывают окно без сохранения; при ошибке введённые данные остаются в окне. Галочки приёмки, качества и упаковки означают фактически выполненные проверки. Отсутствующие проверки и необходимые условия блокируют подтверждение; сервер продолжает проверять права, состояние заказа и версию независимо от интерфейса.

Внизу есть памятка «Как проходит заказ» и отдельная история. Отказ качества и возврат не назначают переделку автоматически: исправление организуется через задачи заказа. Фиксация согласования не отправляет врачу сообщение. Отправка и получение клиникой — разные действия.

Аналитический обзор использует четыре вида графиков: столбцы по этапам с выделением через легенду, состав загрузки команды (срок не просрочен / не задан и просрочен), круг распределения активных работ по клиникам с интерактивной легендой и карту материалов, где размер плитки соответствует числу работ с материалом. Подсказки показывают точные значения; полный список исполнителей доступен под графиком команды. Это текущий срез, без искусственных временных трендов и без оценки производственной мощности.

### Репозиторий GitHub

Для текущего продукта используется один приватный репозиторий. Его корень — содержимое этой папки: `frontend/`, `backend/`, `saas/`, `scripts/`, `ci/`, `storage/`, `compose.yaml` и `.github/`. У фронта, Go-backend и панели SaaS отдельные сборки Docker, но общая история изменений и проверки совместимости. Старые Java-проекты и остальные папки родительского workspace в этот репозиторий не входят.

1. На [GitHub](https://github.com/new) создать пустой **Private** репозиторий `teeth-tech-crm-mvp`. Не добавлять README, лицензию или `.gitignore`: они уже находятся в исходниках.
2. Из этой папки проверить состав первого коммита и подключить адрес созданного репозитория. Для выбранного репозитория `Mussinn/teeth-tech-crm-mvp` команды такие:

   ```sh
   git status --short
   git remote add origin https://github.com/Mussinn/teeth-tech-crm-mvp.git
   git push -u origin main
   ```

   Эти команды предполагают, что локальная ветка `main` и первый коммит уже подготовлены. Для push требуется авторизация Git на компьютере; подключённое приложение GitHub само по себе не авторизует терминал. Вместо команд можно использовать GitHub Desktop и открыть в нём эту папку.

3. Во вкладке **Actions** проверить запуск `CRM checks`. Он проверяет фронт, Go-backend, API-интеграции и Docker-образы. Находки безопасности могут блокировать проверки; устранять причину, а не отключать job ради зелёного результата.
4. `CRM release images` запускается вручную из `main`, повторяет CI и публикует отдельные образы в GHCR. Этот workflow **не разворачивает приложение на сервере**. Для CD нужны тестовый стенд, выбранный сервер и сценарий обновления лабораторий с резервной копией, проверками и откатом.

`.env`, приватные ключи, runtime лабораторий, загрузки, дампы и резервные копии исключены через `.gitignore`. В Git входят `.env.example` с шаблонами настроек. Перед каждой публикацией нужно проверить новые файлы: `.gitignore` не удаляет секреты из уже отслеживаемых файлов и истории коммитов.
